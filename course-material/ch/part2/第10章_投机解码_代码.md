# 第 10 章 投机解码（代码实现）

普通生成每调用一次目标模型，只确认一个新 token。投机解码先让草稿模型提出多个候选，再让目标模型一次验证这些候选。验证通过的连续前缀可以一起提交；遇到不匹配，就纠正并重新起草。

本篇对应[概念篇](./第10章_投机解码.md)。我们用一个只有几个 token 的条件概率表代替神经网络，让接受、拒绝和位置对应都能手算。代码独立运行，不依赖前面章节，也不需要模型权重。先理解贪心路径，再读保持目标分布的随机路径。

## 1 本章学习目标

1. 写出起草 → 验证 → 提交的循环。
2. 找准每个草稿对应的预测行，处理首次拒绝与 bonus token。
3. 用接受概率和残差分布实现随机投机采样。

## 2 先运行一个能手算的例子

只需 Python 3.12 标准库，在仓库根目录执行：

```bash
python3 examples/part2/chapter10/speculative.py
```

贪心部分输出：

```text
greedy: [1, 2, 0, 1, 2, 0, 1, 2]
matches target: True
target_calls=3, accepted/proposed=5/9
```

目标模型单独生成与投机生成的 token 完全一致。程序还会输出一条随机采样序列；随机路径的正确性应检查概率分布，不能要求相同 seed 下逐 token 相等，因为两种算法消费随机数的顺序不同。

### 2.1 条件概率表是什么

`TableModel` 用 `table[i][j]` 表示“当前 token 是 i，下一个 token 是 j 的概率”。目标表如下：

| 当前 token | 下一步为 0 | 下一步为 1 | 下一步为 2 |
| --- | --- | --- | --- |
| 0 | 0.1 | 0.8 | 0.1 |
| 1 | 0.1 | 0.1 | 0.8 |
| 2 | 0.8 | 0.1 | 0.1 |

所以从 0 开始，贪心生成会循环选择 1、2、0。草稿表仅将第二行改为 `[0.1,0.7,0.2]`，让它在 token 1 后故意猜错。

`model(tokens)` 返回每个输入位置之后的条件分布，形式类似对语言模型各行 logits 做 softmax。表模型只依赖最后一个 token；真实因果模型通常依赖整个前缀，但两者的“第 i 行预测第 i+1 个 token”约定相同。target 和 draft 必须使用相同的 token ID 含义，词表大小相同只是必要条件。

## 3 先读贪心路径

### 3.1 起草：逐步扩展临时前缀

令已确认前缀为 `tokens`，每轮最多起草 `draft_steps` 个候选。每一步都把此前的草稿接在前缀后面，因此候选之间有条件依赖。

起草内容保存在临时 `proposals` 中，只有通过验证或被目标纠正的 token 才写回正式前缀。草稿遇到 EOS 时停止继续起草，但这个 EOS 仍需要验证。

### 3.2 验证：一次调用得到 k+1 行

前缀长 `L`，草稿长 `k`。将前缀和草稿一起输入 target，因果性保证每行只能读取它之前的输入：

| target 返回的行号，从 0 开始 | 用途 |
| --- | --- |
| `L-1` | 验证第一个草稿 |
| `L` | 验证第二个草稿 |
| `L+k-2` | 验证最后一个草稿 |
| `L+k-1` | 全接受后选择额外 token |

程序用下面一行取出验证区间：

```python
verification = target(tokens + proposals)[len(tokens) - 1:]
```

如果从 `L` 开始切，第一个候选已经被当成输入读过，验证位置就错了一位。

### 3.3 提交：首次拒绝就停

本例第一轮草稿为 `[1,1,1]`。目标先确认第一个 1，第二个位置却应当是 2，于是本轮提交 `[1,2]`，丢弃后面的草稿。第三个候选对应的条件前缀仍然包含错误的 1，不能继续使用。

若所有草稿都接受，target 最后一行已经预测出它们之后的 token，可以额外提交一个 bonus token。代码使用 Python 的 `for ... else`：只有验证循环没有因拒绝而 `break`，才进入 bonus 分支。

每次提交都检查 EOS 和剩余长度。接受到 EOS、纠正 token 是 EOS、bonus 是 EOS，都立即结束；达到 `max_new_tokens` 后也不会再多发一个 bonus。

## 4 再读随机路径

### 4.1 接受概率

设目标分布为 `p`、草稿分布为 `q`，候选 `y` 已从 `q` 抽出，以如下概率接受：

$$
\min\left(1,\frac{p(y)}{q(y)}\right).
$$

候选从 `q` 抽得，所以 `q(y)>0`。程序保存起草时实际使用的每一步 `q`，验证时取相同条件前缀的 `p`。换成神经网络时，二者都应是实际采样分布；若做温度或 Top-k/Top-p 处理，就必须使用处理后的概率。

### 4.2 拒绝后的纠正分布

拒绝时，从正残差归一化后的分布抽样：

$$
r(v)=\frac{\max(p(v)-q(v),0)}{\sum_u\max(p(u)-q(u),0)}.
$$

例如 `p=[0.4,0.6]`、`q=[0.8,0.2]`。提出 0 时接受概率是 0.5，提出 1 时必定接受；拒绝后只能补 1。最终输出 0 的概率为 `0.8×0.5=0.4`，输出 1 的概率为 `0.2+0.8×0.5=0.6`，恰好恢复目标分布。

一般情况下，接受分支给 token v 的概率质量为 `min(p(v),q(v))`，拒绝校正补齐剩余的正差。因此拒绝后不能简单地重新从 p 抽一次。首次拒绝后的草稿仍需丢弃，下一轮从纠正后的真实前缀重新起草。

## 5 验证正确性，再考虑加速

```bash
python3 -m unittest examples.part2.chapter10.test_speculative -v
```

测试先比较不同草稿长度、全接受和全拒绝时的贪心输出，再检查 EOS、bonus 和零输出。另用依赖完整前缀的模型检查条件位置，避免只在一阶概率表上通过测试。

随机测试从 token 0 开始，用目标表 `[[0.8,0.2],[0.3,0.7]]` 连续生成两个 token。精确联合概率为 `P(00)=0.64、P(01)=0.16、P(10)=0.06、P(11)=0.14`。固定随机种子抽样 10000 次，检查各频率的绝对偏差小于 0.02，并单独检验残差恒等式。

这里每轮重算完整前缀，不维护持久化 KV；只有已提交 token 会进入下一轮。接入真实缓存时，需撤销未接受草稿对应的 KV，纠正或 bonus token 的 KV 也要在它真正前向后才有效。

表查询没有模拟模型耗时，`target_calls` 也不是加速比。实际收益取决于草稿成本、接受长度、目标验证、缓存和采样开销。本例实现线性投机算法；树状验证、EAGLE 和 GPU 内核是进一步的工程主题。

## 6 总结与测试题

### 6.1 课程总结

投机解码先起草，再由目标确认。贪心模式比较候选是否等于目标选择；随机模式用接受概率与正残差保持目标分布。两种路径都只提交连续接受的前缀，首次拒绝后重新起草。

### 6.2 测试题

1. 前缀长 5、草稿长 3，验证草稿和取得 bonus 分别读取哪些行？
2. 把 `draft = target` 后运行，接受率和目标调用次数如何变化？
3. 把拒绝后的残差采样改为直接从 p 采样，联合分布测试会怎样？
4. 草稿产生 EOS、但目标拒绝了它，此时应该提交什么，是否结束请求？
